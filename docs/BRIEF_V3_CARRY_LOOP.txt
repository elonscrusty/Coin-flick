2. ROUND AND ROCK STATE MODEL
Each solo/party match is private to its participants, with up to 4 players. Exactly one shared central pile, not separate piles for each player. Solo uses one assigned station; multiplayer gives each participant one assigned station arranged evenly around that same pile.

Create authoritative records for every eligible round rock:
RockId, RoundId, opaque appearance seed, current state, current carrier/station owner, current cracking progress. Keep target-rock identity server-only. Never put IsGeode, target IDs or clues in replicated attributes, object names, client remotes or client-visible configuration. Clients may know an opaque RockId but not whether it is the winner.

State transitions:
InPile -> Carried -> QueuedAtStation -> Processing -> ResolvedOrdinary or ResolvedGeode.
Interrupted carriers can return to InPile. A processing interruption pauses safely. Only one state/location exists per rock. Use server-side validation and atomic state transitions; never let two players claim the same rock or duplicate a queued rock.

Recommended starting round: 80 unique rock records; retain the existing short tutorial round (e.g. 12 rocks). Select exactly one target uniformly from eligible records at round generation, server-side. Never silently reroll the geode as players collect rocks. Preserve existing configured totals if already intentionally balanced, but expose them as centralized tuning values.

Each exterior is visually neutral. Valuable rock must not glow, be larger, have a special outline, or appear in a predictably privileged position before it is opened.

Counter rules:
- 'Unopened rocks: N' counts all unresolved rocks, including carried/queued/processing; decreases on completed crushing only.
- 'Pile rocks: N' is optional, distinct from unopened count; decreases on pickup, increases on return.
- 'Carrying: X / 5' counts uncrushed rocks in player carry basket.
- 'Rubble: Y / capacity' counts already crushed ordinary material.
Do not reuse the rubble storage counter for uncrushed rocks. Do not claim 'rocks left' means pile count if it actually tracks unresolved rocks.

5. CRUSHING TABLES: LAYOUT AND MODEL
Build four equal processing bays around the single shared pile; assign one per participant. Equal walking distances, matching access width and consistent visibility. In solo, one is active and unused bays are clearly inactive. These are round workstations, not new personal rock piles. Keep hopper separate and retain lobby showroom/gallery.

Starting table model:
- sturdy steel frame with four legs and diagonal braces;
- thick worn wood or metal work surface;
- distinct steel anvil/crushing plate at center;
- input tray holding visible queued whole rocks;
- shallow output tray for rubble;
- side basket docking point;
- small safety shield, rubber pads, bolts and tool hooks;
- yellow industrial corner marking and player-color/nameplate;
- readable station sign and restrained activation light.
Target dimensions roughly 7 studs wide x 4 deep x 3 tall, adjusted to real avatar reach/camera testing. Keep the processing rock visible and centered on the plate. Compose believable industrial props rather than a blank block plus floating label.

User interaction: enter own station range -> contextual DEPOSIT ROCKS -> deposit all carried records atomically into queue, up to station capacity. Start with StationQueueCapacity = 10; partial transfers retain overflow in basket and tell player exactly what happened. Don't discard extras. Input tray must visually represent pending rocks and show accurate queue count.

Next contextual action: HOLD TO CRUSH at own station. Server moves next queued rock to plate and validates processing. Player may choose deposit or crush without fiddly tiny buttons. Support mobile camera that frames player, plate and rock; never locks controls permanently. Another player's station can show progress but must not accept deposit or tool actions.

6. TOOL PROGRESSION MUST PROCESS THE TABLE QUEUE
Preserve existing purchased equipment and economy/configuration where possible. Map tools into this loop:
- Starter Hammer: player swings at the rock ON THE TABLE. Clear visible handle/head, grip, wind-up, contact, recoil. Distinct dent/crack progression and final shell split.
- Steel Hammer: larger readable model; existing damage/cadence upgrades apply at table.
- Jackhammer: player operates it over table plate, with visible bit, short vibration, controlled dust and server-authorized damage pulses.
- Automatic Cracking Machine: machine installed at player's station accepts deposited rocks, feeds and processes them automatically while player returns to central pile to collect more. Do not automatically harvest rocks from pile.
- Hydraulic Press: station machine loads one rock, lowers platen, compresses, splits and raises before next rock. It does not hit every rock in the arena.
- Industrial Crusher: station-attached hopper/conveyor processes deposited queue at upgraded rate with believable synchronized motion. It never replaces all 4 players' equipment or consumes another player's queue.

One active processing mechanism per station, one current rock per station. Do not double-process a rock with a manual tool and machine simultaneously. Manual interaction on an automatic station may deposit/inspect; it must not add unintended extra damage. Preserve existing server cooldowns, progression and ownership checks. Don't change all shop prices merely because carrying was introduced; expose time/queue/damage tuning for playtesting.

Machine owner receives their processed ordinary rubble. If their station finishes the target rock, that owner wins even if elsewhere collecting. Clearly announce this rule in the tutorial and party briefing. Server determines final valid completion; never client timestamps. Upgrades can give the earned speed advantage already intended, without introducing unrelated monetization.

Rubble-capacity policy must not reveal target identity: before starting ANY new rock, reserve enough storage for one ordinary result, regardless of whether the server knows it is the target. If no space is available, pause all new processing and show 'Rubble bag full — sell at hopper'. Preserve queued records and existing progress. An already processing rock finishes against its reserved capacity; an ordinary result consumes that reservation, while a geode releases it and awards the specimen. Reserve server-side, including interactions with sale/storage changes, so no ordinary reward is silently lost. Never let only the target bypass a full-bag pause, which would reveal hidden information. Resume after sale.

7. CRACKING FEEDBACK AND WIN PRESENTATION

Ordinary: short subdued split, rubble enters output/bag, tiny counter update, queue advances.
Geode: slower readable shell opening, rough outer shell plus actual hollow cavity, thick rim and multiple faceted inner crystals with varied heights; compelling colored light concentrated inside. No flat coin/badge standing in for a crystal specimen. On reveal, pause all stations, disable new collection, announce the discovering station/player, present the specimen and results. Ensure queued machine hits are invalidated on round end.

Maintain exactly one geode award and one round resolution. A concurrent second completion cannot award another geode or overwrite winner. Persist via existing idempotent reward path. Solo Find count stays distinct from multiplayer Wins. Other participants retain their personally earned ordinary rubble and receive no consolation geodes.

Ensure tutorial/round cancellation and exiting results do not lose an already committed geode. Give collection entry a stable specimen ID. The recording does not show a new reveal here; verify rather than assert that the prior reveal fix was successful.
